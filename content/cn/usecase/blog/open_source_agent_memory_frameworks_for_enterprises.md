选型时，值得先拿一条真正要上线的需求，看看团队得改哪些代码。[MemOS v2.0.36 的发布记录](https://github.com/MemTensor/MemOS/releases/tag/v2.0.36){target="_blank"}里就有一个具体例子：为了让 PostgreSQL 图存储适配这个版本的接口，改动落在存储层。换成业务规则，团队首先要判断的则是，现有应用能否处理这条规则，什么时候才需要修改记忆服务。

以通知方式为例。一个账号平时接电话，仓库的通知要发短信。今天，经办人又说：“这一次发邮件。”这笔通知应该发邮件，下一笔仓库通知仍应发短信。以后如果撤销仓库的单独设置，通知就该恢复为电话。这几步足以看出，三种框架各自留给团队哪些工作。

## 同一条通知规则，三种改法

| **候选** | **公开可核对的能力** | **这次需求改哪里** | **上线前重点验证** |
| --- | --- | --- | --- |
| **MemOS 开源版** | 多个 Agent 可以通过同一套 [REST 服务](/cn/open_source/getting_started/rest_api_server/)写入和检索记忆。MemReader 处理输入，MemCube 组织记忆，MemScheduler 负责调度。 | 应用根据登录身份确定账号和站点，并决定本次要求、站点设置和账号默认值的优先顺序。需要改变记忆的提取方式、存储组织或后台调度时，再调整对应组件。 | 核对部署版本所需的存储和模型服务。启用异步写入时，检查较早提交的更新晚到后，是否会让已经撤销的设置重新生效。 |
| **Mem0 开源版** | 提供 Python 和 TypeScript SDK，可配置模型、嵌入、向量存储和重排。 | 保留现有运行时。调用方写入偏好时标记适用站点，检索时传入可信的账号和站点条件。 | 官方文档所列的 Python Weaviate 适配器会忽略自定义元数据过滤。采用这个组合时，需要另行落实站点范围，并用同一账号下的两个站点复测。 |
| **Letta 本地后端或自建 App Server** | 提供有状态的 Agent 运行时，MemFS 通过 Git 保留记忆文件的修改历史。 | 团队决定哪些 Agent 可以使用哪些记忆文件，以及通知工具在发送前如何核验审批。 | 自建 App Server 时要确认实际使用的后端。MemFS 默认没有语义索引；如有删除要求，还需考虑 Git 历史和备份中的副本。 |

具体到 MemOS，假设第二笔仓库通知又选了邮件。团队可以先看保存下来的记录。如果“这一次发邮件”被写成了“仓库以后都发邮件”，就该检查 [MemReader 如何从输入中提取记忆](/cn/open_source/modules/mem_reader/)。如果记录里清楚保留了“仅本次”，就沿着[检索和上下文处理流程](/cn/open_source/modules/mos/overview/#_24-对话-chathandler)往下查：系统取回了哪几条记录，应用最后根据哪一条选了邮件。查到这一步，团队才知道该改提取逻辑，还是改通知渠道的选择规则。

有数据驻留要求的团队，还应按实际上线的版本核对两件事：记忆记录存在哪里，抽取和嵌入请求会把哪些内容发给哪个模型服务。

## 先验证业务规则，再比较改造量

下面是一组待执行的试点用例。三个候选使用相同的虚构账号、输入和通过条件。每一步都保留检索结果、模型实际收到的内容，以及测试通知最终选用的渠道。尤其是“本次发邮件”这一条，要查通知工具实际收到的渠道参数。助手在对话里答应了，发送时仍可能选错。

**1. 本次要求能否只生效一次，两个账号能否各用各的偏好**

甲默认接电话，乙默认收邮件。甲先把仓库通知设为短信，再要求“这一次发邮件”。确认本次仓库通知选用邮件。另开一个会话，再给甲的仓库和办公室各发一笔通知：仓库应选短信，办公室应选电话。

接着换成乙，查询乙名下的同名仓库。乙应沿用自己的默认邮件，检索结果和模型输入中都不应出现甲的记录。这里要核对记录归属，因为即使系统碰巧选对了邮件，也有可能读到了甲上一次的临时要求。

**2. 站点设置更正或撤销后，旧值会不会回来**

把甲的仓库通知从短信改为站内信，另开会话，确认仓库通知采用站内信。随后撤销仓库设置，再次查询时，应恢复为账号默认的电话。

采用异步写入的方案，还要再试一次更新顺序：暂缓一笔撤销前提交的站内信更新，等撤销生效后，再让这笔旧更新完成。此时仓库通知仍应选电话。如果又选中了站内信，就对照存储记录、检索结果和会话摘要，看旧值是在哪一步重新进入通知流程的。

**3. 应用退回旧版后，升级期间的变更能否恢复**

另起一组测试，在应用还只支持账号默认值时保存快照。升级到支持站点设置的版本后，把甲的账号默认从电话改为邮件，给仓库和办公室分别设置短信通知，再撤销办公室的设置。这些变更要按顺序保存在回退后仍可读取的业务记录中。

退回旧版后，先恢复账号默认的邮件设置。此时办公室可以继续发邮件，仓库仍有单独的短信要求。如果旧版无法识别这条要求，就根据业务记录暂停仓库的自动通知。重新启用新版并恢复站点变更后，再各发一笔测试通知：仓库应发短信，办公室应发邮件。

三组用例跑完，再比较团队实际改过的调用代码、配置和框架源码，以及回退时需要恢复的数据。如果现有应用在调用侧就能处理这些规则，接入跨会话记忆的改造可以止于这一层。如果几个 Agent 都要用同一套记忆提取或调度逻辑，MemOS 提供了把这部分集中维护的地方。下次通知规则再变，团队就知道该改哪个组件，也知道用哪几笔通知验证改动。
